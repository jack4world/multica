# A remediation item is an ordinary issue with a ledger row beside it

内部审计准则第 2205 号《后续审计》 requires follow-up, and in practice an internal audit function spends more time chasing 整改 than doing fieldwork. The vertical modelled a 整改事项 as "an issue that belongs to no engagement" and stopped there — which gave it no owning department, no verified closure, and nobody told when a deadline passed.

The item stays an ordinary issue. It is assigned, commented on, filtered and searched by every path the platform already has, and its deadline is `issue.due_date` — the column already on every list, board and filter. What audit needs beyond an issue lives in `audit_remediation`, keyed by the issue: the department that owes the fix, the engagement that raised it, and the verification that closed it. The alternative — a separate remediation entity — would have meant re-implementing assignment, comments, search and notification for a second kind of work item.

## Consequences

- **The source engagement is a column, not membership.** An item belongs to no engagement, which is what lets it outlive the audit; `source_project_id` is where the verifier's rank is read from, so an item with no source would have nobody qualified to close it. Moving an item into an engagement is refused for the same reason.
- **The department is a list, not free text.** "本期整改事项按责任部门分布" is the line every follow-up report carries, and 财务部 / 财务处 / 财务部门 as three rows makes that line quietly wrong. `audit_department` is flat — no hierarchy, no membership, and not an access boundary (ADR-0001). A department that owes items cannot be deleted.
- **Closure is a verification, and only a verification.** `pending_verification → remediation_closed` requires a rank on the raising engagement and an account of what was checked, and is closed to the person responsible for the fix — the same independence rule as the review chain, for the same reason. A closed item refuses every further write: a problem that recurs is a new item, not an edited closure.
- **Overdue is derived, never stored and never a status.** A stored flag is only as true as the last job run, and a status a clock sets is a status that lies whenever the clock is not consulted.
- **The overdue notice is sent once.** A deadline that generates a notification every morning trains everyone to ignore the notification, and then the one item that mattered is ignored with the rest. `overdue_reminded_at` is what makes "once" true across restarts and catch-up runs. Both the responsible person and the engagement's 主审 hear it: telling only the first makes the deadline a private matter between one person and a database.
- **The catalog seeds two chains, and seeding is convergent.** The review chain and the remediation chain share a workspace-level status catalog and nothing else — `auditgate` and `remediate` look their statuses up in separate tables so a workpaper moved to 整改中 reads as leaving its chain rather than advancing it. Because the enable endpoint returns early once a workspace is an auditee, it also seeds whatever is missing, which is the only path that reaches an auditee enabled before a chain existed.
